## はじめに

こんにちは、CSIG の市川です。普段は FutureVuls という脆弱性管理サービスの開発・運用を主に担当しており、最近はパフォーマンスの課題に重点的に取り組んでいます。

1 年前に「[4億件のテーブルでSeq Scanが選ばれる問題を、統計情報(n_distinct)の改善で解決するまでのプロセス](/articles/20251010a/)」という記事を書きました。`n_distinct` とは、カラムに含まれる値の種類数を表す統計情報です。

その記事では、「`n_distinct` が実際よりはるかに小さく推定されていた」ことに触れましたが、なぜここまで小さく推定されたのかまでは調査していませんでした (実際には 1,500 万種類ある `parent_id` の `n_distinct` が、統計情報では 67,122 種類と推定されていました)。

本記事では、PostgreSQL の `ANALYZE` が使う推定式と本番のデータを突き合わせ、`n_distinct` が過少に推定された理由を考察していきます。

### 本記事の想定読者

- 巨大なテーブルで、 `n_distinct` が過少に推定されて困っている方
- PostgreSQL が `ANALYZE` で統計情報を計算する際、どのようにレコードをサンプリングしているか、またそのサンプリング方法が `n_distinct` の正確性にどのような影響を及ぼすのかについて、興味がある方
- `n_distinct` の正確性に影響を与える因子について興味がある方
- その他、PostgreSQL の中身の仕組みに興味がある方

### 本記事の読み方

「PostgreSQL に関する前提知識」と「前提となるコンテキストの説明」は、最初は飛ばしていただいても大丈夫です。まず「要約」節からお読みいただき、状況理解に立ち戻りたい際に上の2つの節に戻っていただけると幸いです。その上で、より詳細について気になった方は、「主因」と「副因」節もお読みください。

## PostgreSQL に関する前提知識

今回の説明には PostgreSQL に関する前提知識が 3 つ必要になるため、先にまとめておきます。

### 前提知識①: n_distinct の推定式

`n_distinct` は、列に含まれる値の種類数を表す統計情報です。`ANALYZE` はテーブルの全レコードを走査するのではなく、テーブルから抽出したサンプルのレコードからこの値を推定します。推定には、Haas と Stokes が提案した **Duj1** と呼ばれる推定量が使われています([analyze.c](https://github.com/postgres/postgres/blob/66cdef4425f3295a2cfbce3031b3c0f0b5dffc04/src/backend/commands/analyze.c#L2608-L2646))。

```text
n_distinct = n × d / ((n − f1) + f1 × n / N)
```

| 記号 | 意味 |
| :--- | :--- |
| n | サンプルのレコード数(NULL を除く) |
| N | テーブル全体のレコード数(NULL を除く) |
| d | サンプルに現れた値の種類数 |
| f1 | サンプルにちょうど 1 回だけ現れた値の種類数 |

本記事では、サンプルの中で他のレコードと値が重複したレコードを「**かぶりレコード**」と呼びます。たとえば、サンプルの `parent_id` が `A, A, A, B, B, C, D, E, F, G` の場合、かぶりレコードは A の 3 件と B の 2 件を合わせた計 5 件となります(A は 1 件目も含めて 3 件として数えます)。

1 回だけ現れた値は 1 レコードずつなので、分母の項 `n − f1` はかぶりレコードの数と等しくなります(`analyze.c` の変数 `summultiple`)。分母のもう一方の項 `f1 × n / N` は、$N$ が $n$ よりずっと大きいと小さな値になり、今回の `childs` テーブルでは最大でも約 2 です。そのため、`n_distinct` は次のように近似できます。

```text
n_distinct ≒ d × n / かぶりレコードの数
```

この式から分かるように、**かぶりレコードと `n_distinct` の推定値は反比例します。**

例として、本記事の事例に即した「$n$ = 30,000、$N$ = 約 4.49 億」という状況を考えます。このとき、かぶりレコードの数だけを変えると、`n_distinct` の推定値は次のようになります。

| かぶりレコードの数 | サンプルに占める割合 | 推定 n_distinct |
| ---: | ---: | ---: |
| 20 | 0.07% | 約 4,089 万 |
| 100 | 0.33% | 約 881 万 |
| 300 | 1.00% | 約 297 万 |
| 1,000 | 3.33% | 約 88 万 |
| 3,000 | 10.00% | 約 28 万 |

かぶりレコードがサンプルの 0.07% から 10% に増えると、 `n_distinct` の推定値は 100 分の 1 以下になっていることが分かります。

### 前提知識②: ANALYZE のサンプリング方法

`ANALYZE` がサンプリングするレコード数は、`default_statistics_target`(または列ごとの statistics target)の 300 倍です([analyze.c: std_typanalyze](https://github.com/postgres/postgres/blob/66cdef4425f3295a2cfbce3031b3c0f0b5dffc04/src/backend/commands/analyze.c#L1915-L1938))。statistics target のデフォルト値は 100 なので、既定では 3 万レコードがサンプルとして選ばれます。

この 3 万レコードは、次の 2 段階でサンプリングされます (参考: [analyze.c: acquire_sample_rows](https://github.com/postgres/postgres/blob/66cdef4425f3295a2cfbce3031b3c0f0b5dffc04/src/backend/commands/analyze.c#L1176-L1189))。

1. テーブルの全ページから、サンプルのレコード数と同じ数のページ(既定では 3 万ページ)を無作為に選ぶ
2. 選んだページ内の全レコード中から 3 万レコードを無作為に選ぶ

全レコードから直接 3 万レコードを選ばないのは、読むページ数を抑えて、現実的な時間で終わらせるためと考えられます。(ちなみに、今回の調査で全レコードから無作為に抽出する `TABLESAMPLE BERNOULLI` を 108 GB の `childs` テーブルに対して実行したところ、2 時間たっても終わりませんでした。全ページからサンプリングしようとすると、このように膨大な時間がかかってしまう、ということだと考えられます。)

2 段階でサンプリングすると、同じページにあるレコードどうしが一緒にサンプルに選ばれやすくなります。[`analyze.c` のソースコードコメント](https://github.com/postgres/postgres/blob/66cdef4425f3295a2cfbce3031b3c0f0b5dffc04/src/backend/commands/analyze.c#L1185-L1189)でも、この点に触れています。

> Although every row has an equal chance of ending up in the final sample, this sampling method is not perfect: not every possible sample has an equal chance of being selected. For large relations the number of different blocks represented by the sample tends to be too small. We can live with that for now. Improvements are welcome.

以下の図では例として、全レコードから 1 件ずつ無作為に選ぶ場合(A)と、`ANALYZE` の 2 段階サンプリング (B)を比べています。

<img src="/images/2026/20261127a/sampling.png" class="bordered" alt="" width="532" height="462">

この図では、縦長の枠が 1 ページ、灰色の濃淡の境目が parent の境界です。青はサンプルに選ばれたレコード、橙は同じページから一緒に選ばれた同じ parent のレコードです。B では、サンプリングされるページ数が限られるため、同じページから複数のレコードがサンプリングされる可能性が高くなります。(実際にどれくらい同じページから選ばれやすくなるかについては、「主因」節で詳しく計算します)

### 前提知識③: レコードが insert される際の格納ルール

PostgreSQL のテーブルデータは、8 KB の固定長ページの並びとしてディスクに保存されています(参考: [Database Page Layout](https://www.postgresql.org/docs/current/storage-page-layout.html))。

新しいレコードを `INSERT` するとき、どのページに格納するかは次の順で決まります(参考: [hio.c: RelationGetBufferForTuple](https://github.com/postgres/postgres/blob/66cdef4425f3295a2cfbce3031b3c0f0b5dffc04/src/backend/access/heap/hio.c#L561-L572))。

1. 同一セッションが直前に `INSERT` を行ったページに空きがあれば、そのページに追加する
2. 直前のページに入らなければ、 空き領域マップ (Free Space Map, FSM) から空きのあるページを探す
3. 既存のいずれのページにも空きがなければ、テーブルの末尾に新しいページを追加する

ルール 1 より、同じセッションで続けて insert されたレコードは、ページがいっぱいになるまで同じページに続けて格納されます。

## 前提となるコンテキストの説明

今回の考察にあたり、対象システムのデータ構成に関するコンテキストを 4 点整理します。

### コンテキスト①: テーブルの関係とレコード数

前回の記事と同様に、`parents` テーブルと `childs` テーブルを扱います。`childs` は `parent_id` によって `parents` を外部参照しており、1 つの parent に対して複数の child が紐づく 1:N の関係です。調査時点の規模は次のとおりです。

| 項目 | レコード数 / 種類数 |
| :--- | ---: |
| parents のレコード数 | 約 4,027 万件 |
| childs のレコード数 | 約 4.44 億件 |
| childs.parent_id の種類数(n_distinct の真の値) | 約 4,019 万種類 |

1 つの parent に紐づく child は平均 11.05 件です。(※前回の記事執筆時点では、childs が約 4 億件、`parent_id` の種類数が約 1,500 万件でしたが、前回との違いについては本記事の考察にはあまり関係ないので、気にしないでいただいて大丈夫です。)

### コンテキスト②: `childs.parent_id` の `n_distinct` の推定値

前回の記事の調査時点では、`childs` テーブルの `parent_id` レコードに対して、ANALYZE で計算される `n_distinct` は 67,122 で、真の値(約 1,500 万)の約 230 分の 1 でした。

現在は `n_distinct` を手動で固定しているので、`pg_stats` を見ても `ANALYZE` の推定値は分かりません。そこで今回は、`ANALYZE` のサンプリングと推定の手順を近い条件で再現する SQL を実行し、今のデータでの推定値を計算しました。

再現した推定値は約 17.6 万で、こちらも真の値(4,019 万)の約 230 分の 1 でした。実行した SQL と結果は、補足 主1-3 に載せています。

### コンテキスト③: `childs` テーブルのページ数と 1 ページあたりのレコード数

`childs` テーブルは約 1,418 万ページあります。レコード数をページ数で割ると、1 ページあたり平均 31.7 レコードです。

ただし、レコードが 1 件もない空のページが、全体の約 2 割ありました(VACUUM でデッドタプルが回収された影響と推測されます)。`TABLESAMPLE SYSTEM` で約 3 万ページを選んだところ、レコードが返ってきたのは 23,698 ページでした。

レコードが入っているページだけで数えると、 **1 ページに含まれるレコード数は約 40 個です。**

### コンテキスト④: 同一 parent_id を持つ child が bulk insert されやすい

対象のシステムには、バッチ処理などの影響で、「同じ `parent_id` を持つ `child` が bulk insert されやすい」という性質がありました。

この性質が、前提知識③ の「続けて insert されたレコードは同じページに格納される」という動きと合わさって、**同じ parent のレコードが同じページにまとまって格納された**と推測されます。詳しくは「主因」の節で説明します。

## 今回のケースで `n_distinct` が約 18 万と推定された理由

### 要約: 過少推定を引き起こした 2 つの要因とシミュレーション比較

#### 要因の要約

本番データから `ANALYZE` と同じ方法でサンプルを取って計算したところ、真の値 4,019 万に対して推定値は約 18 万(約 1/230)まで下がりました。 (推定に用いた SQL の実行結果については、補足 主1-3 を参照)この過少推定は、主に次の要因によって生じていました。

- 以下の 2 点が組み合わさったことで、同一 `parent_id` を持つ child レコードが、同一ページ内に密集していた
  - コンテキスト④: 同一 `parent_id` の child が、複数まとめて bulk insert されやすい
  - 前提知識③: 連続して insert されたデータは同一ページへ順次詰め込まれる
- ANALYZE のサンプリング特性:「3 万ページを選んでから、その中で 3 万レコードを選ぶ」(前提知識②) に起因し、同一ページから複数件のレコードが選ばれやすくなっていた
- 「同一ページ内に、同一 `parent_id` を持つ child レコードが複数存在しやすい状況」と、「同一ページから複数レコードが選ばれやすい状況」の 2 つが重なったことで、同一の `parent_id` を持つレコードが複数選ばれやすくなっていた

また、以下も副次的な要因として挙げられます。

- parent ごとの child 件数の偏り(ロングテール分布)
  - child を大量に持つ一部の parent が、かぶりレコードを増やす効果もあった。ただし、主因に比べると寄与度は小さかった

#### データ配置とサンプリング方法ごとの `n_distinct` の推定値の比較

それぞれの要因の影響を切り分けるため、「主因: データの配置」と「副因: データの偏り」を組み合わせた 4 通りのデータを考えます。

- ① 偏りなし × 配置ランダム: すべての parent が 11.05 件ずつ child を持ち、格納順もランダム
- ② 偏りなし × 配置連続: 件数は ① と同じで、ページ内では同じ parent が続けて並ぶ
- ③ 偏りあり × 配置ランダム: parent ごとの件数は本番のままで、格納順はランダム
- ④ 偏りあり × 配置連続: 今の本番データ

:::note
**想定データ配置についての補足**

②・④ の「配置連続」は、各ページ内の約 40 レコードが、同じ parent の 3 件ずつのかたまり約 13 個でできていると仮定して計算します(計算は「主因」節の 4 番を参照)。
:::

各データの組み合わせに対し、2 つのサンプリング方法で `n_distinct` の推定値を計算しました。比較結果は以下のとおりです。

| データ | 全レコードから無作為に 3 万件抽出 | 3 万ページを選び、その中から 3 万レコードを抽出(ANALYZE と同じ) |
| ----- | ----- | ----- |
| ① 偏りなし × 配置ランダム | 約 3,690 万 | 約 3,690 万 |
| ② 偏りなし × 配置連続 | 約 3,690 万 | 約 45 万 |
| ③ 偏りあり × 配置ランダム | 約 327 万 | 約 327 万 |
| ④ 偏りあり × 配置連続(※ **本番データ**) | 約 327 万<br>(※ 実測値は 351 万) | 約 16.3 万<br>(※ 実測値は 17.6 万) |

この表から、次の 2 つが読み取れます。

- ①と②の比較より: 同一 `parent_id` のレコードがページ上に連続して並んでいる場合:
  - 「3 万ページを選び、その中から 3 万レコードを抽出」のサンプリングだと、`n_distinct` の推定値は数十万(約 1/90)まで下がる
  - 「一方、全レコードから無作為抽出」のサンプリングだと、推定値は下がらない
- ①と③の比較より: 並び方に関係なく、データに偏りがあるだけで、推定値は約 1/12 まで下がる

---

さて、`n_distinct` が過少に推定された要因については、ここまでで整理されました。

ここからは、「なぜその要因が、 `n_distinct` の過少推定に影響するのか」について、数式的な説明やより詳細な実測値なども用いながら、詳しく説明していきます。主因である「物理配置 × サンプリング」と、副因である「データの偏り」の仕組みを順に説明します。

### 主因: ページ単位のサンプリングとページ内の並びの掛け合わせ

前提知識①で見たとおり、$N$ (全体のレコード数) が非常に大きい場合、`n_distinct` の推定値はサンプルの中のかぶりレコードの数でほぼ決まります。

$$ \text{n\\_distinct} \approx \frac{d \times n}{\text{かぶりレコードの数}} $$

今回のケースでは、かぶりレコードの数を次の 2 つの因子の掛け算で見積もれます。

- $C$: 同じページから選ばれた 2 レコードの組み合わせの数(サンプリング方法で決まる)
- $p$: その 2 件が同じ parent になる確率(ページ内の並びで決まる)

同じページから選ばれた 2 件が同じ parent になる組み合わせの数は、 $C \times p$ で表せます。同じ parent の組み合わせが 1 つあると、その 2 件はどちらもかぶりレコードになるため、かぶりレコードの数は次のように書けます。

$$ \text{かぶりレコードの数} \approx 2 \times C \times p $$

これを `n_distinct` に代入すると、以下の式が得られます。

$$ \text{n\\_distinct} \approx \frac{n \times d}{2 \times C \times p} $$

記号の意味と、ANALYZE と同じ条件で取ったサンプル(補足 主1-3)での値は次のとおりです。

| 記号 | 意味 | 今回の値 |
|---|---|--:|
| $n$ | サンプルのレコード数 | 30,000 |
| $d$ | サンプルに現れた `parent_id` の種類数 | 27,544 |
| $C$ | 同じページから選ばれた 2 レコードの組み合わせの数 | 20,117 |
| $p$ | 同じページから選ばれた 2 レコードの `parent_id` が同じになる確率 | 0.126 |

$C$ はページのサンプリング方法に、 $p$ は各ページ内の `parent_id` の種類数に、それぞれ左右されます。

以下、各因子の影響をそれぞれ確認し、最後に掛け合わせます。

#### 1. `C` について: `ANALYZE` と同じサンプリング方法では `C` が約 500 倍になる

`ANALYZE` で採用されているサンプリング方法 (先に 3 万ページをサンプリング → その中から 3 万レコードをサンプリング) が、$C$ にどれくらい影響を及ぼすかを、実測値から確かめていきます。

まず、`ANALYZE` と同様のサンプリングを模倣した場合の、各ページから選ばれたレコード数の内訳を実測しました。 (実施した SQL については、補足 主1-3 を参照)結果は以下のとおりでした。

| 1 ページから選ばれたレコード数 | ページ数 | 割合 |
| ---: | ---: | ---: |
| 0 件 | 7,155 | 30.2% |
| 1 件 | 7,919 | 33.4% |
| 2 件 | 5,201 | 21.9% |
| 3 件以上 | 3,423 | 14.4% |

全体の約 36% のページから 2 件以上のレコードが同時に選ばれています。

「3 件選ばれたページなら ${}_3 C_2$ = 3 通り、4 件選ばれたページなら ${}_4 C_2$ = 6 通り…」と組み合わせを数えていくと、同じページから選ばれた 2 件の組み合わせの数 $C$ は **20,117 通り** と計算できます。

これに対し、全レコードから 3 万レコードを無作為に抽出した場合の $C$ の推測値を計算したところ、約 39 通りと算出されました。 (計算方法の詳細は補足 主1-2 を参照)

「先に 3 万ページを選ぶ」というサンプリング方法のために、無作為抽出と比べて**組み合わせの数 $C$ が約 500 倍に増えていることが分かります。**

<details>
<summary>補足 主1-1: 1 ページから選ばれた件数の内訳と、組み合わせの数え方</summary>

1 ページから $x$ 件選ばれたら、そのページでできる 2 件の組み合わせは $x \times (x - 1) / 2$ 通りです。

| 1 ページから選ばれた件数 | 組み合わせの数 |
|--:|--:|
| 2 件(a, b) | 1 通り: (a, b) |
| 3 件(a, b, c) | 3 通り: (a, b)、(a, c)、(b, c) |
| 4 件 | 6 通り |

20,117 通りの内訳は、2 件選ばれた 5,201 ページから 5,201 通り、3 件以上選ばれた 3,423 ページから残りの 14,916 通りです。
</details>

<details>
<summary>補足 主1-2: 無作為に抽出した場合に、同じページから選ばれる 2 件の組み合わせが約 39 通りになる理由</summary>

全レコードから 3 万レコードを無作為に選ぶと、2 件の組み合わせは $\frac{n \times (n - 1)}{2} \approx 4.5$ 億通りあります。ある 2 件が同じページに入っている確率は、「1 件目と同じページにあるほかのレコードの数 ÷ 全レコード数」です。各ページには平均 39.5 件レコードが存在するため、「1 件目と同じページにあるほかのレコードの数」は 38.5 件となります。

よって、 $C$ (同じページから選ばれる 2 件の組み合わせ) は以下のとおり計算されます。

```text
4.5 億 × 38.5 / 4.44 億 ≒ 39 通り
```

選ぶ対象のレコードが 4.44 億個から 94 万個 (選ばれた 3 万ページに含まれるレコード数) に絞られると、2 件が同じページに入る確率は約 470 倍になります。(※ 実測で得られた「約 500 倍」という結果との差は、ページごとのレコード数のばらつきによるものです)
</details>

<details>
<summary>補足 主1-3: 実行した SQL と結果</summary>

`TABLESAMPLE SYSTEM` でページを選び、その中から `ORDER BY random() LIMIT 30000` で 3 万レコードを選んでいます。ANALYZE はページをちょうど 3 万選びますが、`TABLESAMPLE SYSTEM` は各ページを指定した確率で選ぶので、選ばれるページ数は 3 万前後でばらつきます。

```sql
WITH s0 AS MATERIALIZED (
  SELECT (ctid::text::point)[0]::bigint AS blk, parent_id
  FROM childs TABLESAMPLE SYSTEM (0.2116)   -- 3 万ページ ÷ 全ページ数
), s AS MATERIALIZED (
  SELECT blk, parent_id FROM s0 ORDER BY random() LIMIT 30000
), per_page AS (
  SELECT blk, count(*) AS x FROM s GROUP BY blk
), per_page_parent AS (
  SELECT blk, parent_id, count(*) AS y FROM s GROUP BY blk, parent_id
), g AS (
  SELECT parent_id, count(*) AS c FROM s GROUP BY parent_id
)
SELECT
  (SELECT count(DISTINCT blk) FROM s0)                                    AS pages_read,
  (SELECT count(*) FROM s0)                                               AS records_read,
  (SELECT count(DISTINCT blk) FROM s0) - (SELECT count(*) FROM per_page)  AS pages_0,
  (SELECT count(*) FROM per_page WHERE x = 1)                             AS pages_1,
  (SELECT count(*) FROM per_page WHERE x = 2)                             AS pages_2,
  (SELECT count(*) FROM per_page WHERE x >= 3)                            AS pages_3plus,
  (SELECT sum(x * (x - 1) / 2) FROM per_page)                             AS same_page_pairs,
  (SELECT sum(y * (y - 1) / 2) FROM per_page_parent)                      AS same_page_same_parent_pairs,
  count(*)                                    AS d,
  count(*) FILTER (WHERE c = 1)               AS f1,
  count(*) FILTER (WHERE c > 1)               AS nmultiple,
  coalesce(sum(c) FILTER (WHERE c > 1), 0)    AS summultiple,
  round(sum(c) * count(*) / (coalesce(sum(c) FILTER (WHERE c > 1), 0)
        + count(*) FILTER (WHERE c = 1) * sum(c)
          / (SELECT reltuples::numeric FROM pg_class
             WHERE oid = 'childs'::regclass)))                     AS duj1
FROM g;

 pages_read | records_read | pages_0 | pages_1 | pages_2 | pages_3plus | same_page_pairs | same_page_same_parent_pairs |   d   |  f1   | nmultiple | summultiple |  duj1
------------+--------------+---------+---------+---------+-------------+-----------------+-----------------------------+-------+-------+-----------+-------------+--------
      23698 |       940167 |    7155 |    7919 |    5201 |        3423 |           20117 |                        2540 | 27544 | 25302 |      2242 |        4698 | 175824
(1 row)
```

| 列 | 意味 | 実測値 |
|---|---|--:|
| `pages_read` | 選んだページのうち、レコードが入っていたページの数(P) | 23,698 |
| `records_read` | そのページにあったレコードの数 | 940,167 |
| `pages_0`〜`pages_3plus` | 1 ページから 0 件 / 1 件 / 2 件 / 3 件以上が選ばれたページの数 | 7,155 / 7,919 / 5,201 / 3,423 |
| `same_page_pairs` | 同じページから選ばれた 2 件の組み合わせの数(C)。ページごとの x × (x − 1) / 2 の合計 | 20,117 |
| `same_page_same_parent_pairs` | そのうち、2 件の `parent_id` が一致する組み合わせの数(C × p)。ページ・parent ごとの y × (y − 1) / 2 の合計 | 2,540 |
| `summultiple` | かぶりレコードの数 | 4,698 |
| `duj1` | Duj1 の式で計算した推定値 | 175,824 |

</details>

#### 2. p について: 同一 `parent_id` の child が 1 ページに平均 3 レコードずつ入っている

childs の全ページから 1%(約 11 万ページ)をサンプリングして、「1 ページに含まれる `parent_id` の種類数」と「ページ内で同じ `parent_id` が続く「かたまり」の数」の 2 つを実測しました。 (実行した SQL については、補足 主2-1 を参照)

結果は次のとおりです。

| 実測対象 | 実測値 |
|---|---|
| 1 ページあたりのレコード数 | 39.5 |
| 1 ページに含まれる `parent_id` の種類数 | 13.2 |
| ページ内で、同一 `parent_id` が連続して並んでいる「かたまり」の数  | 13.4 |

この結果より、以下の 2 つのことが言えます。

1. 1 つの parent に属する child が、同じページに平均 3 レコードずつ入っている
    - `(1 ページあたりのレコード数) / (1 ページに含まれる parent_id の種類数) = 39.5 / 13.2 ≒ 3`
2. 同じ `parent_id` のレコードが、ページ内で続けて格納されている
    - 「1 ページに含まれる `parent_id` の種類数」と「ページ内のかたまりの数」がほぼ同一

2 点目の要因は、コンテキスト④ の「同じ `parent_id` を持つ child が bulk insert されやすい」ことと推測されます。

1番の「同じページに平均 3 レコードずつ入っている」という状況が $p$ にどのような影響を与えるかを調べるため、並び方ごとに $p$ を比較しました。結果は次のとおりでした。 (※ $p$ を導出する式については、補足 主2-2 参照)

| ページ内での `parent_id` の並び | $p$ |
|---|--:|
| ランダム(1 ページの約 40 件が、ほぼすべて別の parent) な場合の推測値 | 約 4.3 × 10⁻⁷ |
| 約 3 件ずつのかたまりが 13 個、均等に並ぶ場合の推測値 | 約 5% |
| 実測値 (C = 20,117 通りのうち 2,540 通り、補足 主1-3 参照) | 12.6% |

1 ページ内に、同じ `parent_id` のレコードが平均 3 件ずつ存在することで、ランダムな並びの場合と比較して $p$ が非常に大きくなっていることが分かります。

<details>
<summary>補足 主2-1: ページ内の `parent_id` の種類数と、かたまりの数を実測するための SQL</summary>

childs の全ページから 1%(約 11 万ページ)をサンプリングして数えました。1 ページあたりのレコード数が 39.5 なのに対し、1 ページに含まれる `parent_id` は 13.2 種類でした。同一 parent の child が、1 ページの中に平均 3 レコードずつ入っている計算です。

また、ページ内のレコードを格納位置の順に見て、同じ `parent_id` が続く「かたまり」の数も数えました(下の SQL の `runs_per_page`)。`ctid` はレコードの物理的な位置で、`(ページ番号, ページ内の位置)` の組です。ページ内の位置の順に並べ、直前のレコードと `parent_id` が変わったところを新しいかたまりの始まりとして数えています。

```sql
WITH p AS (
  SELECT (ctid::text::point)[0]::bigint AS blk,
         (ctid::text::point)[1]::int    AS lp,
         parent_id
  FROM childs TABLESAMPLE SYSTEM (1)
), r AS (
  SELECT blk, parent_id,
         parent_id IS DISTINCT FROM lag(parent_id) OVER (PARTITION BY blk ORDER BY lp) AS new_run
  FROM p
)
SELECT count(DISTINCT blk)                                                       AS pages,
       round(count(*)::numeric / count(DISTINCT blk), 1)                         AS records_per_page,
       round(count(DISTINCT (blk, parent_id))::numeric / count(DISTINCT blk), 1) AS parents_per_page,
       round(count(*) FILTER (WHERE new_run)::numeric / count(DISTINCT blk), 1)  AS runs_per_page
FROM r;

 pages  | records_per_page | parents_per_page | runs_per_page
--------+------------------+------------------+---------------
 112455 |             39.5 |             13.2 |          13.4
(1 row)
```

</details>

<details>
<summary>補足 主2-2: $p$ を導出する式</summary>

あるページに R 件のレコードがあり、そのうち parent $k$ の child が $c_k$ 件あるとき、このページから選ばれた 2 件が同じ parent になる確率は次のとおりです。

$$ \sum_k \frac{c_k (c_k - 1)}{R (R - 1)} $$

p は、ページごとのこの確率を、そのページから選ばれた 2 件の組み合わせの数で重み付けして平均したものです。
</details>

<details>
<summary>補足 主2-3: かたまりで並ぶ場合とランダムな並びの場合の $p$ を導出し、比較する</summary>

**■ かたまりが均等に並ぶと仮定した場合の推測値(約 5%)**

表で得られた実測値をもとに、以下の仮定を敷きます。

- すべてのページで、1 ページ内に含まれるレコード数が 39.5 件で、その中に `parent_id` が同じ約 2.95 レコードのかたまりが 13.4 個ずつ含まれている

この時、補足 主2-2 の式で $R$ = 39.5、 `parent_id` の数 = 13.4 となり、どのかたまりでも $c_k$ = $R$ / 13.4 ≒ 2.95 となります。これを代入すると、 $p$ は次のとおり計算されます。

$$ p = \sum_k \frac{c_k (c_k - 1)}{R (R - 1)} = (\text{parent の数}) \times \frac{c (c - 1)}{R (R - 1)} = 13.4 \times \frac{2.95 \times 1.95}{39.5 \times 38.5} \approx 0.051 $$

すべてのページが同じ中身なので、どのページでもこの確率は同じです。重み付き平均を取っても、p は同じ約 5.1% になります。

**■ 現在のデータでの実測値(12.6%)**

補足 主1-3 の SQL の結果から計算しました。

$$ p = \frac{C \times p}{C} = \frac{\text{same\\_page\\_same\\_parent\\_pairs}}{\text{same\\_page\\_pairs}} \approx 12.6\% $$

上記の推測値(約 5%)と比べると、実測の 12.6% は約 2.5 倍です。要約の表の ② (約 45 万) と ④ (約 16 万) の差は、ほとんどがこの $p$ の違いから来ています。

**■ 並びがランダムな場合の推測値(約 4.3 × 10⁻⁷)**

並びが完全にランダムな場合、同じページから選ばれた 2 レコードは「テーブル全体から無作為に選んだ 2 レコード」と同じ扱いになります。

そのため、無作為に選んだ 2 レコードが同じ parent になる確率は、parent ごとの「全レコードに占める割合」の 2 乗の和です。

$$ \text{確率} \approx \sum_k \left( \frac{c_k}{N} \right)^2 = \frac{\sum_k c_k^2}{N^2} $$

(※$c_k$ は parent $k$ の child 数、$N$ は全レコード数。厳密には $\frac{c_k(c_k - 1)}{N(N - 1)}$ ですが、分母が大きいので近似できます。)

本番データ($N \approx 4.44 \times 10^8$)の件数分布から計算すると、次のようになります(件数帯の中のばらつきを無視しているので少し小さめの見積もりですが、桁は変わりません)。

- $\sum_{k} c_k^2 \approx 8.5 \times 10^{10}$
- $N^2 \approx 1.97 \times 10^{17}$
- 確率 $\approx 8.5 \times 10^{10} / (1.97 \times 10^{17}) \approx 4.3 \times 10^{-7}$

</details>

#### 3. 2 つの要因が重なってかぶりレコードの数が大きく増加した

1 と 2 で見た $C$ と $p$ の値を組み合わせると、同じページの中で生じるかぶりレコードの数 ($2 \times C \times p$) は次のようになります。

| | 並びがランダム($p$ ≒ 4.3 × 10⁻⁷ (推測値)) | 今の配置($p$ = 0.126 (実測値)) |
|---|--:|--:|
| ランダムサンプリング<br>($C$ ≒ 39 (推測値)) | ほぼ 0 | 2 × 39 × 0.126 ≒ 10 |
| 3 万ページを先にサンプリング<br>($C$ = 20,117 (実測値)) | 2 × 20,117 × 4.3 × 10⁻⁷ ≒ 0.02 | 2 × 2,540 = 5,080 |

**この表より、「3 万ページが先にサンプリングされること」と「1 ページ内に同一 `parent_id` のレコードが複数存在すること」の掛け合わせによって、かぶりレコードの数が非常に大きい値で算出されたことが分かります。**

たとえ現在のように、同じ `parent_id` を持つ child がページ内に複数存在する状況であっても、サンプリング方法がランダムサンプリングなのであれば、同じページの中で生じるかぶりレコードは多くても 10 件ほどです。ここに「3 万ページを先にサンプリングする」という ANALYZE の仕様が加わると、かぶりレコードの数ははじめて約 5,000 件になります。

このかぶりレコードの数を `n_distinct` の式に代入すると、以下の値が得られます。

$$ \text{n\\_distinct} \approx \frac{n \times d}{2 \times C \times p} = \frac{30{,}000 \times 27{,}544}{5{,}080} \approx 162{,}700 $$

実測のかぶりレコード 4,698 件、推定値 175,824 と、おおむね合います。 (実測値については、補足 主1-3参照)

上の表の 4 マスそれぞれについて、`n_distinct` の推定値を並べると次のとおりです(③・④ は、要約の表の行を再掲しています)。

| | 並びがランダム | 今の並び |
|---|--:|--:|
| 無作為抽出 | 推測値: 約 327 万(③) | 推測値: 約 327 万(④)<br>実測値: 351 万 |
| 3 万ページを先にサンプリング | 推測値: 約 327 万(③) | 推測値: 約 16.3 万<br>実測値: 17.6 万(④) |

右下以外の 3 マスでは、 $C$ と $p$ が `n_distinct` にほぼ影響を与えていないことが分かります。

:::note
**補足: 「並びがランダム×無作為抽出」でも `n_distinct` が実際の値よりも小さい理由**

右下以外の 3 マスでは、同じページの中のかぶりレコードはほとんどありません。この場合、`n_distinct` は、別々のページから選ばれたかぶりレコードで決まります。今回のケースでは、データの偏りに起因して別々のページから選ばれたかぶりレコードが約 270 件存在していました。このかぶりは $C$ と $p$ に関係なく生じるので、3 マスとも約 327 万になります。詳しくは、「副因」節で説明します。
:::

#### 4. (補足) 推定値はおよそ P / p で決まる

$C$ は、$P$(選んだページのうち、レコードが入っていたページの数)を使って $C \approx n^2 / (2P)$ と見積もれます(補足 主4-1 参照)。これを代入した場合の推定値は以下のとおりです。

$$ \text{n\\_distinct} \approx \frac{n \times d}{2 \times \frac{n^2}{2P} \times p} = \frac{d}{n} \times \frac{P}{p} = \frac{27{,}544}{30{,}000} \times \frac{23{,}698}{0.126} \approx 172{,}700 $$

この式には、テーブル全体のレコード数 N も parent の数も出てきません。ANALYZE が読むページ数は statistics target の 300 倍(既定では 3 万ページ)で、テーブルが大きくなっても変わりません。また、d / n は 1 を超えないので、推定値は P / p ≒ 18.8 万をほとんど超えません。

ページ内の並びが今と同じなら、テーブルがさらに大きくなっても、推定値は 17〜19 万程度にとどまる計算です。

この式を使うと、要約の表の ② (偏りなし・並びが連続)の値も計算できます。② では各ページの約 40 件が 3 件ずつのかたまりでできているので、$p$ は補足 主2-3 の「均等に並ぶ場合」の約 5.1% です。かぶりレコードは約 1,960 件($ \frac{2 \times n²} {(2P) \times p}$ に、偏りのない分の約 22 件を足した値)で、d / n は約 0.97 になります。

$$ \text{n\\_distinct} \approx \frac{d}{n} \times \frac{P}{p} \approx 0.97 \times \frac{23{,}698}{0.051} \approx 450{,}000 $$

<details>
<summary>補足 主4-1: 同じページから選ばれた 2 件の組み合わせの数が n² / (2P) と見積もれる理由</summary>

$n$ 件から 2 件を取り出す組み合わせは、約 $n² / 2$ 通りあります。そのうち 2 件が同じページに入っている確率はおよそ 1 / P のため、同じページから選ばれた 2 件の組み合わせの数は $n^2 / (2P)$ です。

今回実測した childs テーブルにおいては、$P$ は 2.4 万なので、同じページから選ばれた 2 件の組み合わせの数は以下のように導かれます。

```text
n² / (2P) = 30,000² / (2 × 2.4 万) ≒ 19,000 通り
```

実測の 20,117 通りが少し多いのは、ページごとのレコード数にばらつきがあり、レコードの多いページから多めに選ばれるためです。

</details>

### 副因: parent ごとの child 数の偏りで無作為に抽出してもかぶりレコードが生じる

要約の表の左列(全レコードから無作為に抽出)では、レコードの並び方に関係なく、parent ごとの child の数に偏りがあるだけで、`n_distinct` の推定値が約 327 万(推測値)、実測でも 351 万(真の値の約 1/11)まで下がっています。

この要因を解明するため、ふたたびかぶりレコード数を考えます。今回は、かぶりレコードの数を、「サンプルの中のすべての 2 レコードの組み合わせの数」と「その 2 レコードの `parent_id` が同じになる確率」の掛け算で見積もります。 (主因では、同じページ内から選ばれた 2 レコードのみを考えていました)テーブル全体から無作為に選んだ 2 レコードの `parent_id` が同じになる確率を $q$ とおきます。主因の 2・3 で「並びがランダムな場合の $p$」として使った値(約 4.3 × 10⁻⁷)と同じです(計算方法は補足 主2-3 を参照)。

| | 対象にする 2 件 | 組み合わせの数 | 2 件が同じ parent になる確率 |
|---|---|--:|--:|
| 主因 | 同じページから選ばれた 2 件 | $C$ = 20,117(実測値) | $p$ = 0.126(実測値) |
| 副因 | サンプルの中のすべての 2 件 | $n^2 / 2$ ≒ 4.5 億 | $q$ ≒ 4.3 × 10⁻⁷(推測値) |

parent $k$ の child の数を $c_k$、全レコード数を $N$ とすると、次の式で表せます。

$$ q \approx \sum_k \left( \frac{c_k}{N} \right)^2 $$

同じ parent の組み合わせ 1 つにつき、かぶりレコードが 2 件生じるのも主因と同じです。したがって、かぶりレコードの数の期待値は次の式で近似できます。

$$ \text{かぶりレコードの数} \approx 2 \times \frac{n^2}{2} \times q = \sum_k \left( \frac{n \times c_k}{N} \right)^2 $$

この式から分かるように、**parent $k$ から生じるかぶりレコードの期待値は、$c_k$ の 2 乗に比例します。**(※ ただし、$c_k$ が大きくなってくると、この近似式は実際よりも多く見積もるようになり、ずれが生じます。議論の流れに大きな影響はないため、ここでは説明を割愛します。詳しくは補足 副1-2 を参照してください)

#### 1. q について: 偏りがあると 2 件が同じ parent になる確率が約 17 倍になる

データに偏りがある場合とない場合で、かぶりレコードの数と `n_distinct` を比べると次のとおりです(`n_distinct` は、要約の表の値を再掲しています)。

| データ | $q$ | かぶりレコードの数 | `n_distinct` |
|---|--:|--:|--:|
| ① 偏りなし(すべての parent の child が 11.05 件) | 推測値: 1 / 4,019 万 ≒ 2.5 × 10⁻⁸ | 推測値: 約 22 | 推測値: 約 3,690 万 |
| ③・④ 今の分布 | 推測値: 約 4.3 × 10⁻⁷ | 推測値: 約 270<br>実測値: 253 | 推測値: 約 327 万<br>実測値: 351 万 |

偏りがない場合、$q$ は parent の数の逆数になり、かぶりレコードは約 22 件と推測されます。一方、実際のデータに即した偏りのもとでは、かぶりレコードは 270 個と推測されます。

$q$ は「各 parent が全レコードに占める割合」の 2 乗の和なので、child が多く紐づいている parent がある場合、$q$ は非常に大きくなります。実際、この $q$ の約 1/3 は、child の数が最も多い 12 個の parent によるものです。child が多く紐づく parent が、$q$ を大きく押し上げていることが分かります。

<summary>補足 副1-2: かぶりレコードの期待値(約 270 件)をポアソン分布で計算する</summary>

上記の表では、かぶりレコードの数を「推測値: 約 270」としましたが、本文の近似式 $\sum_k (n \times c_k / N)^2$ で計算すると約 390 件になります。この差が生まれる理由を、ポアソン分布を用いて説明します。

**組み合わせの数から見積もったかぶりレコードの数は、1 つの parent がサンプルに 3 件以上入ると多すぎる**

同じ parent の組み合わせ 1 つには、レコードが 2 件含まれます。1 つの parent がサンプルに 2 件までしか入らなければ、組み合わせどうしでレコードは重ならず、かぶりレコードの数は「組み合わせの数 × 2」です。上の式は、この前提で見積もっています。

3 件以上入ると、1 件のレコードが複数の組み合わせに含まれるので、この見積もりは実際より多くなります。たとえば a, b, c の 3 件が入ると、組み合わせは (a, b)、(a, c)、(b, c) の 3 つで、見積もりは 6 件ですが、実際のかぶりレコードは 3 件です。

| サンプルに入った件数 $x$ | 組み合わせの数 | 組み合わせから見積もった数 $x(x - 1)$ | 実際のかぶりレコード |
|--:|--:|--:|--:|
| 1 | 0 | 0 | 0 |
| 2 | 1 | 2 | 2 |
| 3 | 3 | 6 | 3 |
| 4 | 6 | 12 | 4 |

ほとんどの parent はサンプルに入っても 2 件までなので、問題になりません。しかし、最も多い 63,005 件の parent はサンプルに平均 4.3 件入ります。上記の近似式から見積もると約 18 件ですが、かぶりレコードの数の期待値は約 4.2 件です(計算は後述)。

**かぶりレコードの数を正しく数えるには、1 件だけ入る確率が必要**

parent $k$ の child がサンプルに入る数を $X_k$ とします。かぶりレコードの定義から、parent $k$ から生じるかぶりレコードは、$X_k$ が 2 以上なら $X_k$ 件、1 以下なら 0 件です。$X_k$ と食い違うのは、1 件だけ入った場合です。

$$ \text{parent } k \text{ のかぶりレコードの期待値} = (X_k \text{ の平均}) - (X_k = 1 \text{ になる確率}) $$

「$X_k$ の平均」は、1 レコードがサンプルに入る確率 $n / N$ ≒ 6.8 × 10⁻⁵ に child の数を掛けた値です。これを $\lambda_k$ と置きます。

$$\lambda_k = c_k \times n / N $$

一方、「$X_k = 1$ になる確率」は、$X_k$ が 0 件、1 件、2 件…になる確率の内訳(分布)が分からないと出せません。$q$ からは 2 件ずつの組み合わせの情報しか得られないので、ここで分布の仮定が必要になります。

$X_k$ は、「当たる確率が 6.8 × 10⁻⁵ のくじを $c_k$ 回引いたときの当たりの数」と同じなので、平均 $\lambda_k$ のポアソン分布で近似できます(二項分布で計算しても結果はほぼ同じです)。ポアソン分布では、1 件だけ入る確率は $\lambda_k e^{-\lambda_k}$ です。これを上の式に入れると、次のようになります。

$$ \lambda_k - \lambda_k e^{-\lambda_k} = \lambda_k (1 - e^{-\lambda_k}) $$

- $\lambda_k$ が小さいとき(ほとんどの parent): $1 - e^{-\lambda_k} \approx \lambda_k$ なので、ポアソン分布で計算した parent $k$ のかぶりレコードの期待値は約 $\lambda_k^2$ 件です。また、組み合わせから見積もった近似値(本文の近似式の parent $k$ の項 $(n \times c_k / N)^2$)も $\lambda_k^2$ です。$\lambda_k$ が小さい parent はサンプルに 3 件以上入ることがめったにないので、両者はほぼ一致します。
- $\lambda_k$ が大きいとき(巨大な parent): $e^{-\lambda_k}$ がほぼ 0 なので、かぶりレコードの数の期待値は約 $\lambda_k$ 件です。63,005 件の parent では $\lambda_k = 30{,}000 \times 63{,}005 / (4.44 \times 10^8) \approx 4.3$ なので、期待値は 4.3 × (1 − 0.014) ≒ 4.2 件です。組み合わせから見積もった約 18 件(= $\lambda_k^2$)よりずっと小さくなります。

**件数帯ごとに足し合わせた結果**

補足 副1-1 の件数帯ごとに計算して足し合わせると、$\sum_k \lambda_k^2$(= $n^2 \times q$)では約 390 件、ポアソン分布で計算した式では約 272 件です。差のほとんどは、child が 8,192 件以上ある 46 個の parent から出ています(約 170 件と約 62 件)。

- ① すべての parent が 11.05 件の場合: どの parent も $\lambda_k$ が小さいので、どちらの式でも約 22 件です。
- 推定値は `n_distinct` ≒ n × d / (かぶりレコードの数 + f1 × n / N) で計算しました。

<summary>補足 副1-3: 全レコードから無作為に抽出した実測(SQL と結果)</summary>

全レコードから無作為に 3 万レコードを抽出したときの、かぶりレコードの数と `n_distinct` の推定値を実測しました。

`TABLESAMPLE BERNOULLI` は 2 時間たっても終わらなかったため(前提知識②)、主キー `id` の範囲から乱数で値を引き、実在する `id` のレコードだけを残す方法で抽出しました。どのレコードも同じ確率で当たるので、無作為に抽出したのと同じ性質のサンプルになります。

`summultiple` がかぶりレコードの数(253 件)、`duj1` が `n_distinct` の推定値(351 万)です。

```sql
WITH r AS (
  SELECT min(id) AS lo,
         max(id) AS hi,
         (SELECT reltuples::numeric FROM pg_class WHERE oid = 'public.childs'::regclass) AS n_rows
  FROM childs
), ids AS (
  -- 欠番を考慮し、ヒット率(n_rows / id 範囲)を見込んで多めに乱数生成
  SELECT array_agg(DISTINCT lo + floor(random() * (hi - lo + 1))::bigint) AS a
  FROM r, generate_series(1, ceil(30000 * 1.2 * (hi - lo + 1) / n_rows)::int)
), s AS (
  SELECT parent_id FROM childs
  WHERE id = ANY ((SELECT a FROM ids)::bigint[])
  ORDER BY random() LIMIT 30000
), g AS (
  SELECT parent_id, count(*) AS c FROM s GROUP BY parent_id
), a AS (
  SELECT sum(c) AS n,
         count(*) AS d,
         count(*) FILTER (WHERE c = 1) AS f1,
         count(*) FILTER (WHERE c > 1) AS nmultiple,
         coalesce(sum(c) FILTER (WHERE c > 1), 0) AS summultiple
  FROM g
)
SELECT a.*,
       round(n * d / (summultiple + f1 * n / (SELECT n_rows FROM r))) AS duj1
FROM a;
```

```text
(1 row)
```

#### 2. かぶりレコードの 8 割強は child が 256 件以上ある 0.17% の parent から出る

parent 1 つあたりのかぶりレコードは、紐づく child が数千件までであれば、child の数の 2 乗に比例します(child が多い parent で比例しなくなる理由は、補足 副1-2 を参照)。

| child の数 $c_k$ | サンプルに入る数の平均 $n \times c_k / N$ | かぶりレコード(推測値) |
|--:|--:|--:|
| 11 | 0.00074 | 5.5 × 10⁻⁷ |
| 1,100 | 0.074 | 0.0053 |
| 63,005 | 4.3 | 4.2 |

child が 100 倍になると、かぶりレコードは約 1 万倍になります。最も多い 63,005 件の parent は、サンプルに平均 4 件ほど入るので、ほぼ確実にかぶりレコードを生みます。

これを件数帯ごとに足し合わせると、約 270 件のかぶりレコードの出どころは次のようになります(補足 副1-2 のポアソン分布で計算した推測値)。

| child の数 | parent の数 | 全レコードに占める割合 | かぶりレコード(推測値) | かぶりレコードの内訳 |
|---|--:|--:|--:|--:|
| 1〜7 | 2,151 万 | 17.3% | 1.5 | 0.5% |
| 8〜31 | 1,675 万 | 51.8% | 16 | 6.0% |
| 32〜255 | 186 万 | 21.3% | 29 | 10.7% |
| 256〜1,023 | 60,819 | 7.0% | 82 | 30.2% |

この、child が非常に多く紐づく parent に引っ張られて、種類数が小さく見積もられ、結果として `n_distinct` が実際の値よりも小さく算出されます。

#### 3. (補足) ANALYZE でも偏りによるかぶりは主因と比べて小さい

$q$ はページ内の並びと関係なく、parent ごとの child の数だけで決まります。そのため、ページ単位で抽出する ANALYZE でも、別々のページから選ばれた 2 件については同じ計算が成り立ち、偏りによるかぶりレコードはほぼ同じ件数生じると考えられます。

ANALYZE と同じ条件で取ったサンプル(補足 主1-3)のかぶりレコードは 4,698 件でした。ここから無作為抽出での実測値 253 件(補足 副1-3)を引くと、主因によるかぶりレコードは約 4,450 件(推測値)です。偏りによるかぶりは、全体の約 5% にとどまると推測されます。

## まとめ

本記事では、`ANALYZE` による `childs.parent_id` の `n_distinct` の推定値が、真の値の約 1/230 まで小さくなった仕組みを、推定式とページ内のデータの並びの両面から調べました。

- `n_distinct` の推定値は、サンプルの中のかぶりレコードの数にほぼ反比例します
- 過少推定を引き起こした 2 つの要因:
  1. 【主因】 物理配置とサンプリング方法の組み合わせ: 同じ `parent_id` を持つ複数の `child` レコードが同じページに複数格納されていたうえに、`ANALYZE` がページ単位のサンプリングを実施するため、同じページから同じ `parent_id` を持つレコードが一緒に選ばれることが多くなっていました
      - 同じ parent のレコードが同じページに複数格納されていた理由は、 同一 parent_id を持つ child が bulk insert されやすいことに起因していると推測されます
  2. 【副因】 child の数の偏り: child を大量に持つ parent(最大 6 万件超)があり、そこからもかぶりレコードが生じていました

個人的には、「先にサンプリング対象のページが 3 万個選ばれる」というサンプリング方法が `n_distinct` の過少推定に大きく影響していた、という点が特に興味深かったです。

`n_distinct` が過少に見積もられているのは、対象カラムの値が同一であるレコードをまとめて bulk insert していることが原因の可能性があります。今後もし似た事象 (`n_distinct` が過少に推定される) に遭遇した方がいましたら、この点から調査してみると良いかもしれません。
