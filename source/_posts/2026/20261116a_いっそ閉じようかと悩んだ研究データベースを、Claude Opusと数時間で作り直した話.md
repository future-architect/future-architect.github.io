## はじめに

こんにちは。HIGの中村です。本業とは別に、北海道大学低温科学研究所のタンパク質複合体探索の研究用データベース「[PCoM-DB](https://pcomdb.lowtem.hokudai.ac.jp/proteins/top)」を、ボランティアで開発・運営しています。仕事でコーディングすることはほぼありませんが、システムの仕組みは一通り分かる、という立場です。技術的な詳細も出てきますが、細かいところは読み飛ばしても流れは追えるように書いています。

この記事は、「自分が持っているサイトに脆弱性がたまっているが、直す時間も余力もない。いっそ閉じようか…」と悩んでいる方に向けて書きました。私もその一人でした。

結論から言うと、AI エージェント（Claude Opus）に作業を任せ、自分は「何をするかを承認する」ことに役割を絞ったところ、サイトを閉じずに数時間で作り直せました。その過程で、長い間気づかなかった表示の不具合まで見つかりました。

ここでは、ボランティアで運営する小規模なサイトの脆弱性対応を例に、どう判断し、どう進め、今後どう維持していくかを紹介します。手間をかけられない小さなサイトの維持が前提です。

## きっかけ：GitHub から届いた6通のアラート

2026年11月11日から13日の3日間で、GitHub から「A security advisory on … affects at least one of your repositories」というメールが6通届きました。どれも PCoM-DB のリポジトリ（`Gemfile.lock`）が対象です。

| 受信（日本時間） | ライブラリ | 重要度 | 内容 |
| :---- | :---- | :---- | :---- |
| 11/11 15:16 | rack | High | multipart の解析でメモリを使い切らせるサービス妨害（DoS） |
| 11/11 15:29 | activestorage | High | 動画プレビューや画像処理で、任意ファイルの読み取りと遠隔コード実行のおそれ |
| 11/11 23:01 | activesupport | High | `safe_constantize` でのサービス妨害（DoS） |
| 11/13 17:47 | msgpack | High | 5バイトのメッセージで数GBのメモリを確保させるサービス妨害 |
| 11/13 20:22 | activestorage | **Critical** | 画像解析で、任意ファイルの書き込みと読み取りのおそれ |
| 11/13 22:44 | actionpack | High | Strong Parameters のすり抜けのおそれ |

1通ずつ確かめて直す余力はありません。調べてみると、既知の脆弱性はこの6件だけでなく、全部で246件ありました。

## サイトと、抱えていた悩み

PCoM-DB（Protein Co-Migration Database）は、光合成生物のタンパク質複合体を予測するための公開データベースです。BN-PAGE で分けたゲル断片ごとの LC-MS/MS の結果を、タンパク質の「泳動プロファイル」としてグラフ表示します。

| 項目 | 内容 |
| :---- | :---- |
| データ | 8生物・13試料、測定値 712,250行、タンパク質情報 97,690行 |
| 構成 | Ruby on Rails 7.1 + PostgreSQL（Heroku） |
| 機能 | 閲覧のみ（一覧・検索・グラフ）。ログインや書き込みはなし |
| 運営 | ボランティア（最終更新は2023年6月） |

10年ほど前に公開したサイトで、前回の更新は2023年です。それまでは AI を使わず自力で対応していて、Heroku のスタックのサポート切れに対応するだけでも死にそうでした…。2週末ぐらいつぶしたこともあります。

「このまま維持するのが大変なら閉じた方が良いかも…」というのが、正直な気持ちでした。

## ① 脆弱性チェック：ソース解析と、外からの確認

最初に Claude に頼んだのは、「本番に負担をかけずに脆弱性を調べてほしい」ということでした。調べ方は2つです。

- **ソース解析**：公開リポジトリのコードを手元に取り、brakeman（Rails のコードの静的解析）と bundle-audit（使っている Gem の既知の脆弱性）を実行しました。JavaScript ライブラリの版や、リポジトリに入っているファイルも確認しました。
- **外からの確認**：ホワイトハッカーの視点で、攻撃はせずに、本番サイトの外から見える設定を確認しました。通信の暗号化、セキュリティヘッダ、Cookie の設定です。本番への負担を避けるため、アクセスは数回だけにしました。

| 観点 | 結果 | 評価 |
| :---- | :---- | :---- |
| コードの書き方（brakeman） | SQL インジェクション・XSS は検出なし。警告は Rails 7.1 のサポート終了の1件のみ | 良好 |
| 依存 Gem（bundle-audit） | 既知の脆弱性 246件（Critical 1 / High 30 / Medium 58 / Low 23 / 深刻度不明 134） | 要対応 |
| JavaScript ライブラリ | jQuery 1.8.2（2012年）、Highcharts 4.0.3（2014年）、Lightbox 2.7.1 | 要対応 |
| リポジトリの中身 | Rails の秘密鍵 `config/master.key`、SQLite の DB ファイル、ログ、`node_modules`（約1.4万ファイル）がコミットされていた | 要対応 |
| 通信・Cookie | TLS 1.3、HSTS あり。Cookie の secure / httponly / samesite も設定済み | 良好 |
| セキュリティヘッダ | CSP（読み込めるスクリプトを制限する設定）がない | 要対応 |

結論は「コードの書き方は丁寧だが、フレームワークとライブラリの放置が脆弱性の大半を占める」でした。秘密鍵は `.gitignore` より前にコミットされていたため、追跡され続けていました。`.gitignore` に書いても、一度コミットしたファイルは消えません。中身は Rails 自身の鍵だけで、作り直しの際に新しい鍵に切り替えました。

## ② 対応方針の提案：閉じる・静的にする・作り直す

診断結果をもとに、Claude が4つの選択肢を「運営者の手間・安全性・失うもの」で比べて提案しました。私はその中から「データベースはそのまま、アプリだけを最新の Rails で作り直す」を選びました。

| 選択肢 | 運営者の手間 | 安全性 | 失うもの |
| :---- | :---- | :---- | :---- |
| 今のまま放置 | なし | 低い（脆弱性が増え続ける） | いずれサイトの信頼 |
| 閉じる | なし | ― | 論文からのリンク、研究者の利用 |
| 静的サイトにする | 初回のみ。その後はほぼゼロ | 高い（サーバーで動くプログラムがない） | データベースとしての構成 |
| **最新の Rails で作り直す（採用）** | 初回は承認中心。その後は月数分 | 高い（自動チェックで維持） | なし |

正直なところ、Claude から「静的サイトにする」という案が出てきたことには驚きました…。データベースを HTML ページとして展開する？　ある意味チャレンジングだけど…

Claude によると、データが「閲覧だけ・更新はまれ・合計数MB」という形なら、静的化は十分に現実的だそうです。研究データの公開では実はわりと知られたやり方で、データを事前にファイルにして静的ホスティングに置く方法や、SQLite のファイルごと置いてブラウザ内で SQL を実行する方法もあるとのこと。ただ、業務システムの発想だと「DB があるならサーバーで検索する」が普通なので、最初の選択肢には上がりにくいだろう、だそうです。…SQLite も含まれるならありなのかな…

それでも今回は、データベースの形を残すことにしました。Claude おすすめの HTML 化は、ちょっと現実的じゃないな…という判断です。検索や、好きな遺伝子を重ねて描くグラフを静的ページで再現すると、画面の大半を作り直すことになるからです。論文から張られている URL を保つのにも工夫が要ります。その代わり「URL・画面・機能・データは変えない」を大前提にし、作り直しの影響範囲をアプリ内部に限りました。

方針として合意したのは、次の4つです。

- データベースは変えない（作業前にバックアップを取る）
- URL・画面・機能は変えない
- 本番サイトへの負担を最小限にする
- 作り直したあとの保守を自動化する

## ③ 作業計画と、ステップごとの承認

作業は Claude に任せ、自分は判断に役割を絞りました。Claude が全体を7段階の作業計画にまとめ、各段階の前に作業内容を示します。自分が承認してから着手し、終わったら結果の報告を確かめて、次の段階に進みます。最初に「変更する前、作業前は必ず作業内容を確認して」と伝えておいたことが、安心して任せられた一番の理由です。

| 段階 | 承認した内容 | 確認した結果 |
| :---- | :---- | :---- |
| 1. 現状診断 | ソース解析、本番の外からの確認、DB バックアップの復元 | ①の結果。バックアップから13試料すべてのデータを復元できた |
| 2. 作り直し | 作業用ブランチで Rails 8.1 / Ruby 3.4 に移植。メニューとリンクのデザイン案を選ぶ | 手元で全画面をブラウザ操作し、選んだデザインを画面で確認 |
| 3. 照合テスト | 旧ロジックとの全件照合、本番との照合（2秒間隔で34回） | 不一致は旧サイトの並び順の不具合だけ |
| 4. 確認 | プルリクエストで差分を見る | 自動テスト・brakeman・bundle-audit がすべて成功 |
| 5. 保守の自動化 | GitHub Actions と Dependabot の設定 | CI が成功したときだけ自動デプロイされること |
| 6. 本番切り替え | マージでデプロイ（Heroku の設定は自分で） | 本番で全画面とセキュリティヘッダを確認 |
| 7. DB の改善 | 索引の追加、使っていない表の削除。最後に Heroku のスタックを heroku-26 に更新 | 検索が約8倍速くなり、データ件数は変化なし |

| 担当 | やったこと |
| :---- | :---- |
| Claude | 調査、コードの作成、テスト、照合、プルリクエスト作成、作業記録、本番の動作確認 |
| 自分 | 各段階の承認、デザインの選択、DB バックアップの取得、GitHub との連携、プルリクエストのマージ、Heroku の設定 |

自分の操作はすべてブラウザ上で、コマンドを打つ場面はありませんでした。本番に影響する操作（マージや Heroku の設定）は、すべて自分の手で行いました。

ここからは、作り直しの中身を「依存関係」「セキュリティ」「あわせて直したこと」の順に紹介します。

### 依存関係の見直し

方針は「維持するものを減らす」です。依存が少ないほど、将来の更新作業も少なくなります。結果として、既知の脆弱性は 246件から 0件になりました。

- **Rails 7.1 → 8.1、Ruby 3.3 → 3.4**：段階的な更新ではなく、Rails 8.1 の新しい骨組みに移植しました。小さなアプリではこの方が確実で、古い設定が残りません。
- **Webpacker・jQuery・Lightbox を廃止**：必要な処理は素の JavaScript 約300行に置き換え、`node_modules`（約1.4万ファイル）も不要になりました。
- **Highcharts は最新版（12.x）を同梱**：グラフの見た目と操作性はそのままです。
- **約1,000行のコントローラを約220行に**：試料ごとのコピーペーストを、試料の一覧データによる表示に置き換えました。

### 脆弱性に強いソースに

依存を新しくするだけでなく、万一新しい脆弱性が見つかっても被害が広がりにくい作りにしました。

- **厳格な CSP**：インラインの `<script>` と `onclick` をすべてなくし、`script-src 'self'` を有効にしました。XSS があっても外部のスクリプトは動きません。表の並べ替えスクリプトは `new Function()` を使っていて CSP 下では動かないため、書き直しました。
- **CSRF 対策を外さない**：旧サイトはグラフ画面だけ CSRF の検証を外していました。このフォームだけセッション共通のトークンを使うことで、検証したまま動くようにしました。
- **入力値の検査**：遺伝子 ID の長さと件数に上限を設け、存在しない ID は 404 を返します。LIKE 検索の `%` や `_` は文字として扱います。
- **応答するホスト名を限定**：Host ヘッダの偽装や DNS リバインディングへの対策です。
- **秘密鍵の入れ替え**：公開されていた鍵は使わず、新しい鍵を Heroku の環境変数で管理します。不要なファイルもリポジトリから外しました。
- **古いブラウザは拒否しない**：Rails 8 の既定（`allow_browser`）は外し、研究室の古い環境からも見られるようにしました。

### あわせて直したこと

作り直しと照合の過程で、前版からの不具合も7件直りました（画像の非表示、リンク切れ、500 エラーなど）。中でも、10遺伝子のグラフが途中で折り返して表示されていたのは、SQL に `ORDER BY` がなかったことが原因でした。

DB は最後の段階で、検索に使う列への索引の追加と、使われていない空の表の削除だけを行い、単一検索は 280 ms から 34 ms になりました。

2週末かかったこともある Heroku のスタック更新も、今回は heroku-26 への切り替えボタンを押して再デプロイするだけで済みました。

## 「同じもの」になったかの確かめ方

研究用のデータなので、見た目が同じだけでなく、**表示される数値が一つも変わらないこと**をClaudeが確かめてくれました。本番のバックアップを手元に復元し、旧コードの計算処理をそのまま再現したスクリプトと、新しいアプリが返す HTML を比べています。

| 対象 | 件数 | 不一致 |
| :---- | ----: | ----: |
| 色分けの帯（遺伝子 × 試料の全組み合わせ） | 11,708 | 10 |
| グラフの値（各試料40遺伝子 × 2モード） | 1,040 | 6 |
| ピークリスト（全試料の全 gel スライス） | 777 | 0 |
| 一覧の表示文字 | 650 | 0 |
| 単一検索（相同タンパク質を含む） | 390 | 0 |
| 複数検索（大文字小文字、存在しない ID を含む） | 39 | 0 |
| 試料ごとの一覧 | 13 | 0 |

不一致はすべて、旧サイトの並び順の不具合によるものでした。

さらに、本番サイトにも2秒間隔で34回だけアクセスして照合し、ズレが本番でも実際に起きていることを確かめました。照合の途中で、「1つの試料に相同タンパク質が複数あるとき、どれを表示するか」が旧サイトと食い違うことも見つかり、旧サイトと同じものを選ぶように直しています。

このほかに、自動テスト20件と、ブラウザでの操作確認15項目（グラフの点クリック、並べ替え、検索など）を用意しました。

## 維持の手間を減らす仕組み

作り直しても、放置すれば数年後に同じことになります。そこで、「気づく」と「更新する」を自動化しました。

- **GitHub Actions**：プルリクエストごと、`master` への push ごと、毎月1日に、自動テストと brakeman / bundler-audit を実行します。毎月の実行があるので、コードを変えていなくても、新しく公開された脆弱性に気づけます。
- **Dependabot**：Gem と Actions の更新を、月に1件のプルリクエストにまとめます。自動マージはしません。
- **CI 成功時のみ自動デプロイ**：Heroku の「Wait for GitHub checks to pass before deploy」を有効にしました。

なお、Heroku の「Wait for GitHub checks」は、GitHub Actions の結果（check run）ではなく、コミットステータスを待つ仕組みです。そのままでは CI が成功しても自動デプロイされなかったため、CI の最後に結果をコミットステータスとして書き込むジョブを足しました。

これで、マージから本番反映まで手動操作なしで進むようになりました。DB の変更も Heroku の release phase（`release: bin/rails db:migrate`）で適用され、失敗したらデプロイ自体が止まります。

### これからの運用

| 頻度 | やること |
| :---- | :---- |
| 月1回（自動） | CI の定期実行。失敗したら通知が来る |
| 月1回程度 | Dependabot のプルリクエストを確認してマージ（問題があれば Heroku でロールバック） |
| 年1回程度 | 同梱した Highcharts の更新確認（Dependabot の対象外） |
| 2028年ごろ | Ruby 3.4 のサポート終了（2028年3月）に合わせて更新 |
| 2031年ごろ | Heroku スタック heroku-26 のサポート終了（2031年4月末） |

## 閉じるか迷っている方へ

「直す余力がない」は、思い込みだったのかな…です。やるべきことはまず始めてみることでした。今回やってみて、大事だと感じたことを並べます。

1. **まずバックアップを取る＆読めることを確かめる**：今回の DB バックアップは PostgreSQL 17 の新しい形式で、古いツールでは開けませんでした。取っただけで安心しないこと。
2. **公開リポジトリに秘密情報がないか見る**：`.gitignore` より前にコミットした鍵や DB ファイルは、公開されたままです。
3. **「変えないもの」を先に決める**：URL、データ、機能を変えないと決めると、影響範囲も確かめることも絞れます。
4. **依存を減らす**：使っていない機能やライブラリは、そのまま将来の脆弱性になります。
5. **新旧を数値で照合する**：見た目では分からない旧サイトの不具合まで見つかります。
6. **「気づく」仕組みを入れる**：毎月の自動チェックと更新のプルリクエストがあれば、放置しても気づけます。
7. **AI に任せるときは、確認のルールを最初に伝える**：「作業前に必ず内容を聞かせて」「本番への操作は自分でやる」と決めておくと、安心して任せられます。

それでも維持できないときは、「閉じる」の前に「静的サイトにして残す」という道もあるのかもしれません。サーバーで動くプログラムがなければ攻撃される箇所もほぼなくなる、と Claude は言いますが、業務システム構築屋さんとしては、DB を HTML に展開するやり方にはまだ少し懐疑的です…

## まとめ

サイトは閉じずに済み、以前より安全で、維持しやすくなりました。

きっかけになった6通のアラートも、作り直しを本番に反映した11月15日にすべて「解決済み」になり、未解決のアラートは0件です。

|   | 作り直し前 | 作り直し後 |
| :---- | :---- | :---- |
| フレームワーク | Rails 7.1（サポート終了） | Rails 8.1 / Ruby 3.4 |
| 依存ライブラリの既知の脆弱性 | 246件 | 0件 |
| CSP（セキュリティヘッダ） | なし | 厳格な CSP（`script-src 'self'`） |
| 前版からの不具合 | 画像の非表示、リンク切れ、グラフのずれなど 7件 | すべて修正 |
| リポジトリのファイル数 | 約1万7千 | 約140 |
| コントローラの行数 | 約1,000 | 約220 |
| 単一検索の処理時間（本番データの複製で測定） | 280 ms | 34 ms |
| テスト | なし | 自動テスト20件 + 毎月の脆弱性チェック |
| 本番反映 | チェックなしで自動 | CI 成功時のみ自動 |
